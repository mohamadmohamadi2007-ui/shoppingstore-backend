ShoppingStore Backend — Table Design Draft v1 BRAINSTORM — NOT FINAL

Step 17 scope: move Product off the flat SQLite table into a real Postgres schema with Categories, Products, and Variants (band + cup + color, per the confirmed sizing decision). This is a first pass to react to, not the final design.

Design calls made for this draft (flag anything you'd flip):
  • Product vs Variant split — Product holds shared, non-sellable info (name, description, category, base/list price shown on catalog cards). Variant holds the sellable unit: band + cup + color + its own SKU, stock, and an optional price_override (defaults to the product's price; only set when a specific size/color costs more — e.g. plus-size bands).
  • Categories — one flat-ish table but with a self-referencing parent_id so it can go 2 levels deep (e.g. "Bras" → "Push-up Bras") without a separate tree table.
  • Stock — lives on Variant, since band+cup+color is the actual sellable/stockable unit. Building it now (not deferring to step 18/22) since the column needs to exist before concurrency logic can touch it.
  • Product ↔ Category — one category per product for v1 (simple FK on Product). Noted as an open question below.
Open questions for the brainstorm:
  1. Is base price on Product with a per-variant override the right call, or should all pricing live on Variant only (simpler, but duplicates price across every size/color of the same product)?
  2. Is one category per product enough, or do we need product↔category many-to-many (e.g. a bralette listed under both "Bras" and "New Arrivals")?
  3. Does Category.parent_id actually get used in v1, or is flat fine until we have more inventory?
  4. Variant SKU format — is {product-code}-{band}{cup}-{color} (e.g. BRA001-34B-BLK) good enough, or do we want a separate barcode/EAN field for POS/label printing later?

How the mock rows relate

  • Products 1–4 (bras) point at categories 2 ("Push-up"), 4 ("Wireless"), 3 ("Sports") — demonstrating the parent/child category link.
  • Product 1 ("Classic Push-up Bra") has 4 variants: two colors of the same 34B, a 36C that's sold out (stock_qty = 0) to show a stock-out case, and a 38D with a price_override to show the larger-band-costs-more case.
  • Products 5–9 use size_label instead of band/cup, showing the "mutually exclusive" rule in the Variant table.
  • Product 10 has is_active = false and intentionally has no variants yet — a case worth deciding: should a product be allowed to exist with zero variants (e.g. "coming soon")?
