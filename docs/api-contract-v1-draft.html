Auth

OTP-based login only (no password). Successful verify returns a JWT in access_token. Send it on every authenticated call as Authorization: Bearer <token>. No refresh-token flow in Phase 1 — token lifetime and re-login-on-expiry behavior is an open question to settle before Emma builds the auth screens.

Pagination

List endpoints that can grow unbounded (products, orders, logs, returns) accept page (1-based) and page_size (default 20, max 100) and return the Paginated<T> envelope documented in the Data Contracts tab. Small, bounded lists (categories, a cart, a product's variants/images) return a plain array.

Error format

Every non-2xx response body:

{
  "error": {
    "code": "OUT_OF_STOCK",
    "message": "Human-readable message, Persian in production.",
    "fields": { "variant_id": "only present for field-level validation errors" }
  }
}

HTTP status still carries the category: 400 validation, 401 missing/invalid token, 403 wrong role or not-your-resource, 404 not found, 409 conflict (stock, duplicate, invalid state transition), 500 server error.

Money & dates

  • All amounts are integers in Rial — no decimals, no minor-unit conversion.
  • All timestamps are ISO 8601 in UTC (e.g. 2026-10-24T14:05:00Z); the frontend converts to Persian calendar / local display.

RTL / i18n

API does not localize strings — all user-facing copy (status labels, error messages) is translated and laid out RTL on the frontend side. The API returns raw enum values and raw numbers only.

Open questions before Emma starts (carried over from this brainstorm)

  • JSON field casing: snake_case (as drafted) vs camelCase.
  • Comment moderation: no status/is_approved column exists yet on Comment — needs a schema decision.
  • JWT lifetime + refresh strategy.
  • Exchange-order creation on an approved return-with-exchange: automatic vs admin-triggered.
